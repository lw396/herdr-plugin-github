# herdr-plugin-github

A Herdr mod, written in TypeScript in `src/github/`, built to `mods/github/`. Read `README.md` first.

## Sources of truth

- The plan: GitHub issue #1 on `lw396/herdr-plugin-github` (the map: decisions and order) and
  its sub-issues, one per step. Scope decisions in `docs/adr/`, words in `GLOSSARY.md`.

- `types/herdr.d.ts` and `types/gpui-kit.d.ts`: the full API for the Herdr version in
  `types/VERSION`. Generated by Herdr; refresh with `bun run types`, never edit.
- `docs/herdr/AGENTS.md`: Herdr's guide (mods, layouts, commands, keys).
- `docs/reference/` (git-ignored, local only): working mods to copy patterns from (`changes` for git + focused folder,
  `files` for lazy trees, `t4-threads` for `gh` calls, `tmux-prefix` for keys/overlays).
  Read-only; not type-checked. Missing in a fresh clone: copy from `defaults/mods/` of
  github.com/herdrdev/herdr-app and from github.com/herdrdev/herdr-layout-examples.

## Source and output

- `src/github/` is the whole source: `*.ts`, `mod.json`, assets (`*.svg`). `mods/github/` is
  build output only (`scripts/build.sh`: tsc for `*.ts`, one file per source with comments kept;
  everything else copied). Never edit it, but commit it: people install that folder as it is.
- Folders, each importing only what is listed (`test/layers.test.ts` checks core/ and io/):
  `core/` pure logic, imports only `core/`; `io/` the outside (`herdr`, programs) and `core/`;
  `views/` the UI, one file per role; `main.ts` picks the role. Assets in `assets/`, referenced
  as `mods/github/assets/<file>`.
- Herdr cannot load `.ts` and resolves only `gpui-kit`, `gpui-base`, `herdr` and the mod's own
  relative files: no npm packages at run time. Import siblings as `./x.ts` (rewritten to `./x.js`).
- `mods/tabs-github/` and `layouts/github.json` are copies of Herdr 0.1.13's shipped `tabs` mod
  and `main` layout (plain JS/JSON, not built). Keep them as close to the originals as possible:
  changes in `tabs-github` are marked `herdr-plugin-github`; the layout renames the tab bar mod,
  adds the `github` child to `panel-body`, and uses GitHub's `pane` role for pane headers.
  `src/github/views/pane.ts` adapts the shipped `pane` header only to add GitHub's logo/name;
  preserve terminal headers and controls. On a Herdr upgrade, recopy the layout/tab bar,
  compare `views/pane.ts` with the new shipped header, and reapply these changes.
- Erasable TypeScript only (`erasableSyntaxOnly`): no `enum`, `namespace` or constructor parameter
  properties, so the output is the source minus its types.

## Runtime limits (Herdr 0.1.13)

- `exec`: 30 s, 8 MiB output, no stdin, no shell. Long work (`gh run watch`) belongs in a terminal
  (`run("terminal.open", { argv })`), not in `exec`; poll instead.
- `exec` with `on` runs through `hc exec --on <machine>`: no shell and no `.bashrc`, the PATH is the
  remote herdr-core's. A missing program rejects with `cannot start <cmd>` (`cannot run <cmd>` here).
- `fetch` gives no response headers (no ETag, rate limit or `Link` pages), refuses Authorization
  across cross-origin redirects (Actions logs and artifacts) and decodes bodies as text. Use `gh`.
- `image()`/`svg()` take paths under the app home only: download remote images first.
- Timers keep running while a copy is hidden: poll gently. Herdr's live data (`spaces()`,
  `focused()`, ...) re-renders the mod by itself: never poll it.

## Rules

- Everything that reaches GitHub goes through `io/gh.ts`. Logic that can be pure goes in `core/`.
- `gh api --jq` prints plain text (strings unquoted): read it with `apiText()`, not `api()`.
- Never keep a `cx`; use the one each callback gets. No `setTimeout`: `cx.timer`, `cx.spawn`.
- `git` and `gh` both run on the folder's machine (ADR 0003): `git` with `{ cwd, on }` from
  `io/context.ts`, `gh` with the `on` from `gh.account()` (no falling back to this computer), so
  remote machines need git and a signed-in gh. Give gh `owner/repo` from `githubRemote()`:
  never a `cwd`, never gh's `{owner}/{repo}` placeholders.
- Use `theme()` colors (`colors()` in `views/ui.ts`). In window overlays, stop mouse-down on controls.
- `herdr-app check` runs `init()` for real: keep `init()` free of side effects beyond reads.
- Never open a Herdr window (`herdr-app` with no subcommand) with a changed `HOME` or
  `HERDR_APP_HOME`: it reaches the real core and can overwrite every machine's spaces.
- Done means `bun run verify` passes (build, typecheck, tests, `herdr-app check`), then tried in the app.
  `herdr-app check` loads mods only: a broken layout shows in `layouts/github.error` in the app home.

## Developing

- The app runs on the person's Mac, not on this dev server (no display): agents can't see the UI.
  `bun run dev` rebuilds `mods/github/`; mutagen mirrors `mods/github/`, `mods/tabs-github/` and
  `layouts/github.json` into the Mac's `~/.config/herdr-app/`; Herdr hot-reloads. Ask the person
  for `herdr-app status` (load errors: a broken save keeps the old build running) or a screenshot.
- `bun run check` needs `herdr-app` on PATH. Without an install here, download the release
  tarball (`releases.herdr.dev/app/latest.json`) into a temp folder and use only its subcommands.
- Herdr upgrade: `bun run types` from an app home of the new version, then recopy its `tabs` mod
  and `main` layout into `mods/tabs-github/` and `layouts/github.json` and reapply our changes.
- Theme picks and panel sizes are saved per layout: switching to `github` doesn't bring `main`'s.

## Test-driven

Prefer TDD (the `tdd` skill): red, then green, one vertical slice at a time. Agree the seams
before writing tests. Expected values come from real gh/git/GitHub output or the docs, not
recomputed by the code. The seams:

- `core/`: command arguments, parsing, turning GitHub data into what the UI shows. Put new
  logic here first. Tests in `test/core/`.
- `io/` (`gh.ts`, `git.ts`, `context.ts`, `known.ts`, `issues.ts`), tests in `test/io/`: under Bun, `herdr` is `test/fake-herdr.ts`
  (`test/preload.ts`). `exec` is faked as machines answering commands: `machine(on, { "<cwd>$ <cmd>": reply })`,
  with replies copied from running the real command (stdout, stderr, exit code); a Promise as the
  reply is a slow machine, answering when the test resolves it (for ordering). An unknown
  command rejects like a missing program does in Herdr. `spaces`, `panes` and `focused` are faked
  as a screen: `screen({ spaces, panes, focused })`, shaped like `herdr-app status` shows. The fake
  has only these: when `io/` starts using another `herdr` function, add it to `test/fake-herdr.ts` first.
- `views/` and `main.ts`: kept thin; checked by `herdr-app check` and by trying them in the app.

When a bug shows up in the app, first reproduce it as a failing test in `core/` or `io/`
(e.g. the real output that broke parsing), then fix.
